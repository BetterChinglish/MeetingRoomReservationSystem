# PRD 分册 02 — 预约管理

> 本分册隶属于总纲 `D:\exam\prd\PRD.md`，是会议室预约系统的**核心分册**，仅覆盖「预约生命周期」领域：预约创建、时段冲突判定、状态机、未开始/已开始的判定时点、取消、提前结束、预约列表查询、并发抢时段与防重复提交。用户与权限、会议室与部门主数据、数据看板、非功能性需求等由其他分册承载，本文仅在必要处引用其术语，不展开。
>
> 技术栈上下文：Java 17 + Spring Boot 3 / MySQL 8 / Redis 7 / Vue 3 + Element Plus；鉴权采用 JWT。
>
> 术语对齐：角色枚举 `EMPLOYEE / ADMIN`、预约状态枚举 `PENDING / ACTIVE / ENDED / CANCELLED`、会议室状态 `ENABLED / DISABLED`，均与分册 01、03 保持一致。

---

## 1. 概述

预约管理是本系统价值链的中间环节，向上承接用户登录后的业务意图，向下为数据看板提供统计源数据。其核心职责包括：

1. **预约创建**：员工/管理员填写必要信息后提交，系统在保证「同一会议室同一日期同一时段不重叠」的前提下落库。
2. **时段冲突判定**：以显性算法判定目标区间与已有有效预约区间是否相交，覆盖相邻、包含、部分重叠、起止相等等边界。
3. **状态机管理**：定义 `PENDING → ACTIVE → ENDED` 主流与 `PENDING → CANCELLED`、`ACTIVE → ENDED(提前结束)` 支流，并显性列出非法流转。
4. **判定时点与时区**：以预约日期 + 起止时间与「当前时间」比较决定状态自然流转的触发点，统一时区口径。
5. **取消 / 提前结束**：按角色与归属区分本人/任意、未开始/已开始的权限边界。
6. **列表查询**：按高频关键字段筛选，区分员工与管理员视图。
7. **并发与防重**：用 Redis 解决并发抢同一时段与重复提交问题。

本分册目标：为后续 Spec 编写与编码实现提供**无歧义**的业务规则、字段要点、边界条件与验收标准。

## 3. 隐性需求

原始需求未明写、但为保障系统正确性与可用性必须落实的需求：

1. **登录后才能预约**：未登录用户不可进入预约表单/列表；身份上下文来自 JWT（见分册 01），不信任前端传入的 `userId` 作为操作者。
2. **预约人不可手工改写**：员工创建预约时，`user_id` 由服务端从 JWT 注入；即使前端传入也以 JWT 为准。管理员代他人创建预约属 MVP 之外能力，不在本分册承诺。
3. **会议室停用拦截**：被选择会议室处于 `DISABLED` 时不可创建新预约（规则引用分册 03 的 BR-R8）；后端在冲突校验前先校验会议室状态。
4. **状态自然流转**：`PENDING → ACTIVE`、`ACTIVE → ENDED` 不需要用户主动触发，由系统按当前时间与预约时间判定；查询/读取时即时计算，或在定时任务/读取时点驱动状态刷新。
5. **时区口径**：所有「当前时间」与预约日期/起止时间的比较统一使用服务端时区（默认 `Asia/Shanghai`，UTC+8），数据库以 `DATETIME` 存储、不涉及时区转换；前端展示与入参均按该时区的本地时间。
6. **跨天拒绝**：`end_time` 必须严格大于 `start_time`，且两者必须落在同一日期内（MVP 限定）；跨天入参直接返回参数校验错误。
7. **主题非空且长度限制**：`title` 不可为空字符串或仅空格，需有最大长度（建议 100 字符），防止超长输入。
8. **时间粒度**：起止时间建议以 30 分钟为最小粒度对齐（如 09:00、09:30），便于排期与冲突判定一致性；MVP 不强制做粒度校验，但前端时间选择器按 30 分钟步长生成候选。
9. **历史不可改写**：已结束（`ENDED`）或已取消（`CANCELLED`）的预约不可再修改任何字段（包括取消、提前结束、编辑）；仅 `PENDING / ACTIVE` 在各自规则下可流转。
10. **并发抢同一时段**：两个请求几乎同时为同一会议室同一时段创建预约，系统必须保证仅一条成功，另一条返回冲突错误，不能两条都落库。
11. **防重复提交**：用户因网络抖动或双击在短时间内对同一预约内容多次提交，系统需识别为重复并拦截，避免产生多条相同记录。
12. **取消/提前结束的副作用**（已按评审建议1补充）：取消后该时段即释放，可被他人重新预约；提前结束后**仍按原 `[start_time, end_time)` 全区间占位**，剩余时段**不可复用**（即不释放、不引入 `actual_end_time` 双字段，与 4.7 BR-RV-21/48/49 统一）。占用时长统计口径由看板分册定义，本分册建议按 `start_time → 原 endTime` 计算。
13. **操作审计（轻量）**：取消、提前结束等关键状态流转建议记录操作人、操作时间、操作前后状态（日志即可，MVP 不强制审计表）。
14. **空结果友好提示**：列表筛选无匹配数据时，前端展示空状态文案而非空白表格。
15. **列表默认范围**：员工进入列表页默认看到全部预约（不限本人），与"所有员工可查询所有会议室预约情况"对齐；是否默认按日期/状态预筛由前端决定，但后端接口必须支持不传筛选条件即返回全量分页。

## 4. 业务规则

### 4.1 预约创建

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-01 | 必填字段：`roomId`、`reserveDate`、`startTime`、`endTime`、`userId`（服务端注入）、`deptId`、`title`；任一缺失返回 400 参数校验错误。 |
| BR-RV-02 | `reserveDate` 为日期类型（`YYYY-MM-DD`），不接受带时间的字符串；非日期格式返回 400。 |
| BR-RV-03 | `startTime` / `endTime` 为 `HH:mm` 字符串（或等价的 LocalTime），且 `endTime > startTime`；相等或反序返回 400。 |
| BR-RV-04 | MVP 限定单日：`startTime` 与 `endTime` 必须在同一预约日期内，不存在跨天；接口不接受跨天入参（无需额外字段表达跨天）。 |
| BR-RV-04a | 拒绝过去时段（已按评审建议6补充）：创建时服务端以服务端时区当前时间 `now` 为准，若 `combine(reserveDate, startTime) < now`，返回业务错误"不可预约过去时段"；前端可同步禁选过去时段以减少无效提交。 |
| BR-RV-05 | `title` 经 `trim` 后非空，最大长度 100 字符；前后端各校验一次。 |
| BR-RV-06 | `roomId` 必须指向存在的会议室，且该会议室 `status = ENABLED`；停用或不存在返回业务错误（如"会议室已停用"）。 |
| BR-RV-07 | `deptId` 必须指向存在的部门；不存在返回业务错误。 |
| BR-RV-08 | `userId` 由服务端从 JWT 注入，忽略请求体中的 `userId`（若前端误传）；管理员代他人创建不在 MVP 范围。 |
| BR-RV-09 | 创建时预约的初始状态固定为 `PENDING`，不接受前端指定其他状态。 |
| BR-RV-10 | 创建前必须通过时段冲突校验（见 4.3）；冲突返回业务错误"该时段已被预约"，并尽量返回冲突的已有预约概要（主题、起止时间、预约人）便于用户调整。 |
| BR-RV-11 | 创建前必须通过防重复提交校验（见 4.6）；命中返回业务错误"请勿重复提交"。 |
| BR-RV-12 | 创建动作必须在数据库事务内完成冲突校验与插入，并对该 `(room_id, reserve_date)` 维度加行锁或等价排他保护，防止并发同时段双写（见 4.5）。 |
| BR-RV-13 | 创建成功返回新增预约的完整 DTO（含 id、状态、各字段），前端据此跳转列表或详情。 |
| BR-RV-13a | 不提供编辑接口（已按评审建议4补充）：MVP 不提供预约字段（主题、起止时间、会议室、部门等）的修改接口；已创建预约如需调整，请取消后重新创建。 |

### 4.2 预约状态机

状态枚举与语义：

| 状态 | 名称 | 语义 |
| :-- | :-- | :-- |
| `PENDING` | 未开始 | 预约已创建，当前时间未到 `reserveDate + startTime` |
| `ACTIVE` | 已开始 | 当前时间已进入 `[startTime, endTime)` 区间，且未被提前结束 |
| `ENDED` | 已结束 | 当前时间到达或超过 `endTime` 自然结束；或处于 `ACTIVE` 时被提前结束 |
| `CANCELLED` | 已取消 | 处于 `PENDING` 时被取消；不再占用时段 |

合法流转：

```
        创建
         │
         ▼
      PENDING ─────────────取消(本人/管理员)────────────► CANCELLED
         │
         │  当前时间 ≥ 预约开始时间(自然触发)
         ▼
       ACTIVE ──────提前结束(本人/管理员)──────────────► ENDED(提前结束)
         │
         │  当前时间 ≥ 预约结束时间(自然触发)
         ▼
       ENDED(自然结束)
```

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-14 | 合法流转仅限：`PENDING → ACTIVE`、`PENDING → CANCELLED`、`ACTIVE → ENDED`。 |
| BR-RV-15 | 非法流转一律拒绝并返回业务错误"当前状态不允许该操作"（已按评审建议12补充）：`CANCELLED → 任意`、`ENDED → 任意`、`ACTIVE → CANCELLED`、`ACTIVE → PENDING`、`PENDING → ENDED`（不经 ACTIVE 的提前结束）等；**任意状态到自身的自环**（`PENDING → PENDING`、`ACTIVE → ACTIVE`、`ENDED → ENDED`、`CANCELLED → CANCELLED`）也属非法，统一拒绝（取消/提前结束接口对已处于目标终态的记录返回业务错误，而非 200）。 |
| BR-RV-16 | `PENDING → ACTIVE` 与 `ACTIVE → ENDED(自然结束)` 为系统按当前时间自动判定，不由用户显式调用；可在读取/查询时即时计算"虚拟状态"，或由定时任务/延迟队列持久化状态。无论何种实现，对外暴露的状态必须与"当前时间 vs 预约时间"的判定结果一致。 |
| BR-RV-17 | `PENDING → CANCELLED`、`ACTIVE → ENDED(提前结束)` 为用户主动操作，需走对应接口并满足权限（见 4.4）。 |
| BR-RV-18 | 已是 `CANCELLED` 或 `ENDED` 的记录不再参与任何状态流转，亦不再参与冲突判定（见 4.3 的"有效"定义）。 |
| BR-RV-19 | 状态字段以数据库存储值为准；若采用"读取时即时计算虚拟状态"的实现，需保证 `CANCELLED` 与 `ENDED(提前结束)` 这两种**人为终点**被持久化，不会因时间推移被"自然结束"覆盖。 |

### 4.3 时段冲突判定算法

**定义**（已按评审建议6补充）：对于同一 `room_id` 且同一 `reserve_date`，设已存在的有效预约集合为 `S = { r | r.status ≠ CANCELLED 且 ¬(r.status = ENDED 且 当前时间 ≥ combine(r.reserveDate, r.end_time)) }`。新预约区间为 `[s_new, e_new)`。则冲突当且仅当：

```
∃ r ∈ S,  使得  r.start_time < e_new  AND  s_new < r.end_time
```

即两区间 `[s_new, e_new)` 与 `[r.start_time, r.end_time)` **半开区间相交**。

**等价判定**：`NOT (e_new ≤ r.start_time  OR  r.end_time ≤ s_new)`。

边界用例（设新预约 `[09:00, 10:00)`）：

| 用例 | 已有预约 | 关系 | 判定 |
| :-- | :-- | :-- | :-- |
| 相邻-前 | `[08:00, 09:00)` | e_existing = s_new | 不冲突 |
| 相邻-后 | `[10:00, 11:00)` | s_existing = e_new | 不冲突 |
| 完全包含（新包旧） | `[09:15, 09:45)` | 旧完全在新内 | 冲突 |
| 完全包含（旧包新） | `[08:00, 11:00)` | 新完全在旧内 | 冲突 |
| 部分重叠-前 | `[08:30, 09:30)` | 头部重叠 | 冲突 |
| 部分重叠-后 | `[09:30, 10:30)` | 尾部重叠 | 冲突 |
| 起止相等 | `[09:00, 10:00)` | 完全相同 | 冲突 |
| 仅起点等于他人终点 | `[08:00, 09:00)` | 已在"相邻-前"列出 | 不冲突 |
| 仅终点等于他人起点 | `[10:00, 11:00)` | 已在"相邻-后"列出 | 不冲突 |
| 已取消 | `[09:00, 10:00)` 且 `status=CANCELLED` | 不在 `S` 中 | 不冲突 |
| 已自然结束且过 endTime | `[09:00, 10:00)` 且 `status=ENDED`、当前时间 ≥ 10:00 | 不在 `S` 中 | 不冲突 |

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-20 | 冲突判定使用半开区间 `[start_time, end_time)`；`end_time` 不计入占用，相邻时段不视为冲突。 |
| BR-RV-21 | 仅与"有效"预约比较（已按评审建议6补充）；"有效"集合 `S = { r | r.status ≠ CANCELLED 且 ¬(r.status = ENDED 且 当前时间 ≥ combine(r.reserveDate, r.end_time)) }`。`ACTIVE` 与提前结束产生的 `ENDED` 在其原 `[start_time, end_time)` 区间内仍占位（详见 4.7）；自然结束或提前结束且当前时间已过 `end_time` 的 `ENDED` 记录不再参与冲突（因其时段已过去，且新预约已被 BR-RV-04a 过去时段拒绝规则拦截）。 |
| BR-RV-22 | 冲突判定维度为 `room_id + reserve_date`；不同会议室、不同日期不互相冲突。 |
| BR-RV-23 | 冲突判定与创建在同一事务、对 `(room_id, reserve_date)` 加行锁后执行，确保并发安全（见 4.5）。 |
| BR-RV-24 | 冲突时返回业务错误码 + 冲突的已有预约概要（主题、起止时间、预约人姓名），HTTP 状态码建议 409 Conflict。 |

### 4.4 取消与提前结束

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-25 | 取消接口入参为预约 `id`；服务端按 id 查询记录，不存在返回 404。 |
| BR-RV-26 | 取消前置校验（已按评审建议3补充）：以 `computeStatus(record, now)`（按服务端时钟即时计算，见 7.1）的计算值为准，必须为 `PENDING`，否则返回业务错误"仅未开始预约可取消"（即 `ACTIVE/ENDED/CANCELLED` 均不可取消）。不直接以数据库存储的 `status` 字段判定，避免存储态为 `PENDING` 但当前时间已进入区间（即时态为 `ACTIVE`）时被错误取消。 |
| BR-RV-27 | 取消权限：若 `jwtUserId == reservation.user_id`，允许；否则需 `role == ADMIN`，否则返回 403。 |
| BR-RV-28 | 取消成功后状态置为 `CANCELLED`，记录 `updated_at`；该预约时段立即释放，可被他人重新预约。 |
| BR-RV-29 | 提前结束接口入参为预约 `id`；服务端按 id 查询记录，不存在返回 404。 |
| BR-RV-30 | 提前结束前置校验（已按评审建议3补充）：以 `computeStatus(record, now)` 的计算值为准，必须为 `ACTIVE`，否则返回业务错误"仅已开始预约可提前结束"（`PENDING/ENDED/CANCELLED` 均不可）。即存储态为 `PENDING` 但当前时间已进入区间时，即时态为 `ACTIVE`，可被提前结束；存储态为 `PENDING` 且未到开始时间时，不可提前结束。 |
| BR-RV-31 | 提前结束权限：若 `jwtUserId == reservation.user_id`，允许；否则需 `role == ADMIN`，否则返回 403。 |
| BR-RV-32 | 提前结束成功后状态置为 `ENDED`，记录 `updated_at`；释放后的剩余时段可被他人预约（见 4.7）。 |
| BR-RV-33 | 取消与提前结束均不可对 `ENDED / CANCELLED` 历史记录执行，统一返回业务错误，不返回 500。 |
| BR-RV-34 | 取消与提前结束均不信任请求体中的 `userId` 作为操作者；操作者身份仅取自 JWT。 |

### 4.5 并发抢同一时段

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-35 | 创建预约的 Service 方法以 `@Transactional` 包裹，隔离级别至少 `REPEATABLE READ`（MySQL 默认）。 |
| BR-RV-36 | 在事务内对该 `room_id + reserve_date` 维度加排他锁（已按评审建议11补充）：**优先**使用细粒度 `SELECT ... FROM reservation WHERE room_id=? AND reserve_date=? ... FOR UPDATE`，仅锁该会议室该日期的行，并发度最优；若该日期无现存记录导致无行可锁，可退化为对会议室行 `SELECT ... FROM meeting_room WHERE id=? FOR UPDATE` 作为**粗粒度兜底**，代价是同一会议室不同日期的并发创建会被串行化、吞吐下降，仅作兜底不推荐作为主方案。 |
| BR-RV-37 | 并发场景下，后获取锁的请求必须在先请求提交/回滚后重新基于最新数据做冲突判定，确保只有一条成功。 |
| BR-RV-38 | 不依赖应用层"先查后插"的无锁实现作为唯一保障；必须有数据库层锁或唯一约束兜底。 |
| BR-RV-39 | 锁等待超时配置（`innodb_lock_wait_timeout`）应在合理范围（如 5~10 秒），避免长事务拖垮整库；超时返回业务错误"系统繁忙，请稍后重试"。 |

### 4.6 防重复提交（Redis）

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-40 | 防重键设计（已按评审建议7补充）：`reservation:submit_lock:{userId}:{md5(roomId|reserveDate|startTime|endTime|title)}`，类型 String，值任意（如 1），TTL 默认 5 秒。`title` 纳入 hash 的设计意图：同一用户在短时间内对同一时段提交不同主题视为不同业务意图（如先临时占位后改正式主题），不拦截；同一时段同一主题短时重复则视为误操作拦截。防重**仅覆盖创建接口**，取消、提前结束、查询接口不应用此键。 |
| BR-RV-41 | 提交时先 `SET key 1 NX EX 5`：若返回成功则继续创建流程；若返回失败（键已存在）则直接返回业务错误"请勿重复提交"。 |
| BR-RV-42 | 防重锁在创建流程结束（成功或失败）后不主动删除，由 TTL 自然过期，避免极短时间内的双击/重放。 |
| BR-RV-43 | 防重与冲突校验是两层独立保护：防重针对"同一用户同一内容短时重复"，冲突针对"不同用户/不同请求抢同一时段"，两者缺一不可。 |
| BR-RV-44 | 防重键的 TTL 可配置（默认 5 秒）；过短易漏防，过长易误拦合理连约，需在 Spec 阶段最终确认。 |
| BR-RV-45 | Redis 不可用时，防重降级策略：记录告警日志并放行（不阻塞主流程），由数据库事务与冲突校验保证最终一致性；不可因 Redis 不可用而整体拒绝创建。 |

### 4.7 提前结束对占用时长与冲突的影响

| 规则编号 | 规则 |
| :-- | :-- |
| BR-RV-48 | 提前结束后，该预约在冲突判定中仍按原 `[start_time, end_time)` 区间参与比较（MVP 简化处理，不做"部分释放"）；这是 MVP 决策项，需在 Spec 与看板分册中明确。 |
| BR-RV-49 | 提前结束后该会议室该日期的"剩余时段"（实际结束时间 ~ 原结束时间）**不可**被新预约直接复用（因冲突判定仍按原区间），除非用户主动调整新预约区间避开原区间；MVP 不实现"剩余时段自动可预约"。 |
| BR-RV-50 | 看板的"占用时长"统计口径由看板分册定义（已按第2轮评审建议1补充）；本分册占用时长按 `原 endTime - start_time` 计算（与决策 A 一致，不取 min、不引入 `actual_end_time`），最终以看板分册为准。 |

> 注：4.7 的 MVP 简化决策（提前结束后仍按原区间占位）需在 Spec 阶段再次评审；若改为"按实际结束时间释放剩余时段"，则冲突判定中 `ACTIVE/ENDED(提前结束)` 记录的 `end_time` 应取实际结束时间，需新增 `actual_end_time` 字段。本分册默认采用简化方案。

## 6. 边界条件

1. **起止时间相等**：`startTime == endTime` 视为零时长，返回 400 参数校验错误。
2. **结束早于开始**：`endTime < startTime` 返回 400；前端时间选择器应禁止选择，后端兜底校验。
3. **跨天预约**：MVP 不支持；如 `startTime=23:00, endTime=01:00`（次日）一律按 400 拒绝，不尝试解析为跨天。
4. **过去日期/过去时段**（已按评审建议6补充）：后端**强制拒绝**过去时段，按 BR-RV-04a 执行；前端同步禁选过去时段以减少无效提交。
5. **会议室停用时创建**：返回业务错误"会议室已停用"，错误码与冲突错误区分，便于前端差异化提示。
6. **取消已取消的预约**：返回业务错误"仅未开始预约可取消"，不返回 500，不重复扣减时段。
7. **提前结束已结束的预约**：返回业务错误"仅已开始预约可提前结束"。
8. **员工越权取消/提前结束他人预约**：返回 403，记录状态不变。
9. **并发抢同一时段**：仅一条成功，另一条返回 409 冲突错误，错误信息提示冲突的已有预约。
10. **重复提交**：5 秒内同一用户同一内容多次提交，仅第一次进入创建流程，其余返回"请勿重复提交"。
11. **Redis 不可用**：防重降级放行，由 DB 事务保证一致性；记录告警日志。
12. **时间粒度不对齐**：如提交 `09:17`，MVP 后端不强制对齐到 30 分钟，但前端按 30 分钟步长生成候选；若需严格对齐，在 Spec 阶段追加规则。
13. **主题超长**：超过 100 字符返回 400；前端 `maxlength` 限制。
14. **主题仅空格**：`trim` 后为空视为缺失，返回 400。
15. **状态字段非法值**：数据库 CHECK 约束拒绝；应用层读取到非法值时按 `PENDING` 处理并记录告警。
16. **列表筛选取值非法**：`status` 传入非枚举值返回 400；`page/size` 非正整数返回 400。
17. **分页超界**：`page` 超过总页数返回空 `list`，`total` 仍返回真实总数。
18. **时区偏差**：服务端统一 `Asia/Shanghai`；客户端机器时区不一致时，前端展示以服务端返回的本地时间为准，不做客户端本地时区转换。
19. **夏令时**：`Asia/Shanghai` 无夏令时，无需额外处理；若部署到其他时区需在 Spec 阶段重新确认。
20. **删除用户/部门/会议室的引用**（已按评审建议5补充）：与分册 01、03 一致，不物理删除被引用对象；预约记录的 `user_id/room_id/dept_id` 引用完整性由外键约束或软删策略保证。软删除/改名后，预约列表与详情的名称展示取预约表冗余快照字段 `room_name/dept_name/user_name`（见 BR-RV-61 与 5.1），并对已停用/已删除对象加退化标签。

## 7. 状态机与时区口径补充

### 7.1 状态即时判定伪代码

```
function computeStatus(reservation, now):
    if reservation.status == CANCELLED:        # 人为终点，持久化
        return CANCELLED
    if reservation.status == ENDED:            # 人为终点（提前结束或已自然结束持久化）
        return ENDED
    # 以下为按时间即时判定
    startDT = combine(reservation.reserveDate, reservation.start_time)  # 服务端时区
    endDT   = combine(reservation.reserveDate, reservation.end_time)
    if now < startDT:
        return PENDING
    if startDT <= now < endDT:
        return ACTIVE
    if now >= endDT:
        return ENDED   # 自然结束
```

实现选择：

- **方案 A（读取时即时计算）**：表中 `status` 只持久化 `PENDING / CANCELLED / ENDED(提前结束)`，`ACTIVE` 与 `ENDED(自然结束)` 在查询时由上式计算。优点：无需定时任务；缺点：查询时需带时间计算，索引利用稍复杂。
- **方案 B（定时任务刷新）**：定时任务（如每分钟）扫描即将开始/结束的预约，批量更新 `status`。优点：查询直接读字段；缺点：有刷新延迟，且任务故障时状态不准。
- **方案 C（延迟队列）**：创建时调度两个延迟任务（到 `startTime` 改 ACTIVE、到 `endTime` 改 ENDED）。优点：精准；缺点：依赖队列可靠性。

MVP 推荐方案 A（读取时即时计算），并在 Spec 阶段最终确认。无论选哪种，对外暴露的状态必须与"当前时间 vs 预约时间"的判定结果一致（BR-RV-16、BR-RV-58）。

> 方案 A 补充说明（已按第2轮评审建议6补充）：方案 A 下 `ACTIVE` **不会落库**（存储态只持久化 `PENDING / CANCELLED / ENDED`，其中 `ENDED` 含提前结束与自然结束的持久化终点）；数据库 `status` 字段的 CHECK 约束仍保留 `ACTIVE` 取值仅为**防御性约束**（防止历史数据或迁移遗留出现非法值），正常运行路径不会写入 `ACTIVE`。

> 状态口径二元性（决策 E，已按第2轮评审建议2补充）：`computeStatus` 即时态用于"取消/提前结束前置判定 + 列表/详情状态展示 + `status` 筛选"；看板统计仍用**存储态 `status`**（看板分册定义）。即"看板用存储态、列表展示用即时态"。BR-RV-16"对外暴露的状态必须与当前时间判定一致"适用于列表/详情展示与 `status` 筛选，不约束看板统计口径。

### 7.2 时区口径

- 服务端 JVM 时区固定为 `Asia/Shanghai`（UTC+8），通过启动参数 `-Duser.timezone=Asia/Shanghai` 或配置 `spring.jackson.time-zone` 显式设定。
- 数据库连接串显式指定 `serverTimezone=Asia/Shanghai`；`reserve_date` 用 `DATE`、`start_time/end_time` 用 `TIME`、`created_at/updated_at` 用 `DATETIME`，均不涉及时区转换。
- 前端入参的日期与时间均为服务端时区的本地时间字符串（`YYYY-MM-DD`、`HH:mm`），不携带时区偏移。
- 所有"当前时间"比较在服务端完成，不依赖客户端时钟。

### 8.3 状态机

| 编号 | 验收项 | 期望结果 |
| :-- | :-- | :-- |
| AC-RV-20 | 创建后初始状态 | PENDING |
| AC-RV-21 | 当前时间进入区间 | 列表/详情展示状态为 ACTIVE |
| AC-RV-22 | 当前时间超过 endTime | 列表/详情展示状态为 ENDED（自然结束） |
| AC-RV-23 | 对 ACTIVE 记录调用取消接口 | 返回业务错误"预约已开始，不可取消"或统一为 BR-RV-15 的"当前状态不允许该操作"（已按第2轮评审建议5补充） |
| AC-RV-24 | 对 ENDED 记录调用提前结束接口 | 返回业务错误"预约已结束，不可提前结束"或统一为 BR-RV-15 的"当前状态不允许该操作"（已按第2轮评审建议5补充） |
| AC-RV-25 | 对 CANCELLED 记录调用取消/提前结束 | 返回业务错误，状态不变 |
| AC-RV-26 | 对 PENDING 记录调用提前结束接口 | 返回业务错误"预约尚未开始，不可提前结束"或统一为 BR-RV-15 的"当前状态不允许该操作"（已按第2轮评审建议5补充） |

> ACTIVE 态验收用例构造说明（已按评审建议8补充）：AC-RV-21/23/30/31/32 等涉及 `ACTIVE` 态的用例，统一通过 `reserveDate = 今日、startTime = 当前时间 - 5min、endTime = 当前时间 + 30min` 构造，使 `computeStatus` 即时计算为 `ACTIVE`；**不要直接改库 `status` 字段**为 `ACTIVE`，以免存储态与即时态不一致、偏离方案 A 的口径。`ENDED`（自然结束）态用例用 `endTime = 当前时间 - 5min` 构造；`PENDING` 态用例用 `startTime = 当前时间 + 1h` 构造。

## 9. 与其他分册的衔接关系

- **分册 01 用户与权限**：本分册的"本人/任意"操作权限判定规则引用分册 01 的角色枚举与 JWT 上下文；操作者身份来源、越权防护由分册 01 落地，本分册只声明业务侧权限要求。
- **分册 03 会议室与部门**：本分册的创建前置校验（会议室 `ENABLED`、部门存在）引用分册 03 的主数据与状态规则；下拉数据来源、字段展示格式由分册 03 定义。**差异提示（已按评审建议5补充）**：分册 03 对"改名/改位置/改容量"采用"自然跟随当前值"口径，本分册为应对软删除/改名导致历史预约名称悬空，在预约表冗余 `room_name/dept_name/user_name` 快照字段（见 5.1、BR-RV-61），展示取快照值；该差异需在 Spec 阶段与分册 03 协调一致（建议 Spec 统一采用快照口径，或分册 03 修订为快照口径）。
- **分册 04 数据看板**：本分册产生的预约记录（含 `status / dept_id / room_id / reserve_date / start_time / end_time`）是看板的统计源数据；占用时长的口径（尤其提前结束后）由看板分册最终定义，本分册提供建议。
- **分册 05 非功能与风险**：并发抢时段、防重复提交、时区口径等本分册涉及的实现要求，需在非功能分册中复核性能、可用性与风险等级；本分册仅给出业务规则。

## 10. MVP 边界与决策项汇总

| 决策项 | 决策 | 备注 |
| :-- | :-- | :-- |
| 跨天预约 | 不支持 | 单日内起止时间，跨天入参拒绝 |
| 时间粒度 | 30 分钟步长（前端候选） | 后端不强制对齐校验 |
| 管理员代他人创建 | 不支持 | `user_id` 由 JWT 注入 |
| 状态自然流转实现 | 读取时即时计算（方案 A） | Spec 阶段最终确认 |
| 状态口径（二元，已按第2轮评审建议2补充） | 列表/详情展示 + 取消/提前结束前置判定 + status 筛选用 `computeStatus` 即时态；看板统计用存储态 `status` | BR-RV-16"对外暴露的状态必须与当前时间判定一致"适用于列表/详情展示与 status 筛选；看板统计走存储态 |
| 提前结束后剩余时段 | 不释放、按原区间占位（已按评审建议1定稿） | 不引入 actual_end_time 双字段，与 BR-RV-21/48/49 一致；占用时长按原 endTime - start_time（与决策 A 一致） |
| 过去日期/时段校验 | 后端强制拒绝（已按评审建议6定稿） | 按 BR-RV-04a，前端同步禁选 |
| 列表数据可见范围 | 全量公共可见，权限差异在操作按钮 | 与"所有员工可查询所有预约情况"对齐 |
| 人员维度查询 | 员工强制绑定本人（已按评审建议2定稿） | 与 01 AUTH-14a/AC-U-23 对齐 |
| 防重 TTL | 5 秒（可配置），仅覆盖创建接口 | Spec 阶段确认 |
| 冲突响应码 | HTTP 409 | 业务错误码体系以 Spec 为准 |
| 时区 | `Asia/Shanghai`（UTC+8） | 服务端统一 |
| 预约编辑/修改接口 | 不提供（已按评审建议4/13补充） | 调整需取消后重建，见 BR-RV-13a |
| 批量操作（批量取消/批量创建/批量提前结束） | 不提供（已按评审建议13补充） | MVP 仅支持单条操作 |

| ENDED 过 endTime 参与冲突 | 不参与（已按评审建议6补充） | 见 BR-RV-21 |
