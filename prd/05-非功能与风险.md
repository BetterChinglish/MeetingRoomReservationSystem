## 1. 概述

本分册为会议室预约系统提供横向的非功能性约束与风险管控依据，目标是确保系统在「单位行政日常使用」场景下足够**快、稳、安全、合规**，并明确 MVP 阶段的取舍边界，避免范围蔓延。文档面向后续的规格编写（`D:\exam\spec\`）、编码实现、测试与部署环节，作为非功能验收的统一基准。

本分册定义：

- 性能要求（并发预约、看板查询、列表查询）；
- 安全要求（JWT、密码哈希、SQL 注入、越权、输入校验、XSS）；
- 可用性与可靠性（数据一致性、事务、容错）；
- 兼容性（仅 Web 端，主流浏览器）；
- 合规与数据风险（个人信息最小化、敏感数据保护）；
- 业务风险清单与对策；
- MVP 边界（明确不做项）；
- 跨分册隐性需求汇总；
- 非功能验收标准。

## 2. 非功能需求

### 2.1 性能

> 量纲说明：响应时间指从请求到达后端到响应首字节返回的 P95 时延，测试环境为考场服务器（MySQL/Redis 同机或低网络延迟）。并发量级参考单位规模（百人级），非互联网高并发场景。
>
> 压测方法（已按评审建议13补充）：使用 JMeter 或 Gatling 压测，**预热 30s 后采样 3 分钟**，P95 统计**剔除冷启动**期间样本；并发线程梯度递增（如 10/50/100），每梯度独立采样；DB 连接池、Redis、JVM 均预热完成后再开始正式采样。

| 编号 | 指标项 | 目标值 | 测量条件 / 备注 |
| :-- | :-- | :-- | :-- |
| PERF-01 | **并发预约抢同一时段** | 100 并发请求同一会议室同一时段，仅 1 笔成功，其余返回冲突错误；整体 P95 ≤ 800ms | 模拟 100 个并发线程同时提交同一 `room_id + reserve_date + [start,end)`；要求借助数据库唯一约束/行锁或分布式锁保证不出现重复占用 |
| PERF-01a | **并发对同一预约执行取消/提前结束**（已按评审建议4补充） | 50 并发请求对同一预约同时执行取消或提前结束，仅 1 笔成功流转状态，其余返回 409（状态非法/已被他人变更）或明确提示「记录状态已变更」；整体 P95 ≤ 600ms | 依赖 DB 行锁（`SELECT ... FOR UPDATE`）+ 状态机乐观校验（CAS on `status`），避免重复流转；验收见 AC-NF-27 |
| PERF-02 | **看板查询响应（按日期）** | P95 ≤ 1.5s | 单日维度，会议室 ≤ 20、预约记录 ≤ 1000 条；返回聚合后的图表数据 |
| PERF-03 | **看板查询响应（按月份）** | P95 ≤ 2.5s | 单月维度，需聚合整月数据；建议走 Redis 缓存或预聚合 |
| PERF-04 | **列表查询响应** | P95 ≤ 800ms | 默认分页（如 20 条/页），含常用筛选（会议室/日期/部门/状态）；走索引，禁止全表扫描 |
| PERF-05 | **登录响应** | P95 ≤ 500ms | 含 BCrypt（cost=10）校验 |
| PERF-06 | **新建预约响应（无冲突）** | P95 ≤ 600ms | 含冲突校验 + 写库 + 事务提交 |
| PERF-07 | **JVM 启动时间** | ≤ 30s | 后端容器冷启动到健康检查通过 |
| PERF-08 | **前端首屏加载** | ≤ 3s（生产构建，Nginx 托管，Gzip） | 不含外网 CDN 依赖，建议依赖本地化 |
| PERF-09 | **数据库连接池** | HikariCP `maximumPoolSize` ≥ 20，`connectionTimeout` 10s | 避免连接耗尽导致请求堆积 |
| PERF-10 | **Redis 缓存命中率（看板）** | ≥ 80%（相同筛选条件下重复查询） | 缓存失效策略见 2.4 |

性能保障要求：

- 冲突校验必须**应用层 + 数据库层双保险**：应用层先以查询过滤候选记录，数据库层以排他约束或行锁最终裁定，避免并发下两个事务同时通过应用校验后双写。
- 看板查询走预聚合或缓存，禁止每次查询对全表 `GROUP BY` 扫描；缓存 key 含维度参数，数据变更时按会议室/日期粒度失效。
- 列表查询分页必须基于索引覆盖，避免深分页 `OFFSET` 过大（可限制最大页码或采用游标分页）。

### 2.3 可用性与可靠性

| 编号 | 指标项 | 要求 |
| :-- | :-- | :-- |
| AVAIL-01 | **服务可用率** | 考场单机部署下，正常工作时段可用率目标 ≥ 99%（非严格 SLA，排除计划停机） |
| AVAIL-02 | **数据一致性** | 预约创建/取消/提前结束必须事务化；冲突校验与写入在同一事务内，避免半成功状态 |
| AVAIL-03 | **事务隔离** | 默认 `READ COMMITTED`；冲突校验关键路径使用行锁或排他约束，避免幻读导致双占 |
| AVAIL-04 | **失败幂等** | 预约提交支持幂等键（前端生成 UUID，服务端 Redis 短期去重），避免网络重试导致重复预约 |
| AVAIL-05 | **状态机一致性** | 预约状态流转必须在 Service 层原子完成；不允许跨状态跳跃（如 `PENDING` 直接到 `ENDED`），违规流转返回 409 |
| AVAIL-06 | **缓存与库的一致性** | 看板缓存写操作触发失效（预约创建/取消/提前结束后失效对应 `room_id + date` 缓存）；容忍短时弱一致，但不可出现已取消预约仍计入占用时长 |
| AVAIL-06a | **缓存防穿透/雪崩/击穿**（已按评审建议7补充） | ① **防穿透**：空结果以短 TTL（如 60s）缓存，避免恶意查询反复击穿到 DB；② **防雪崩**：缓存 TTL 加随机抖动 **±60s**（基准 TTL 5 分钟则实际 TTL 4~6 分钟），避免大量 key 同时过期；③ **防击穿**：热点 key（如看板当日总览）miss 时加**互斥锁 / single-flight**（Redis `SETNX` 或本地锁），仅一个线程回源 DB，其余等待结果；或采用「永不过期 + 异步刷新」策略（key 不设 TTL，由写操作触发异步刷新）。三策略组合使用 | 与 2.4 联动 |
| AVAIL-07 | **优雅降级** | Redis 不可用时，鉴权降级为仅校验 JWT 签名（不查黑名单，记录告警）；看板降级为直接查库；不导致整体不可用 |
| AVAIL-08 | **健康检查** | 后端提供 `/api/health` 返回应用 + DB + Redis 连通状态，供 Docker/Nginx 探活 |

| AVAIL-09 | **日志可观测** | 统一日志格式（时间/级别/traceId/用户/接口），关键操作（登录、预约、取消、提前结束、越权拦截）记录 INFO/ WARN 日志 |

| AVAIL-10 | **异常可恢复** | 后端异常不导致进程退出；全局异常处理器统一返回错误码与友好提示；事务异常自动回滚 |
| AVAIL-11 | **时钟一致性** | 「未开始/已开始」判定以**服务端时钟**为准，前端时钟偏差不影响状态判定；服务端时区固定为 `Asia/Shanghai` |

#### 2.3.1 预约状态自动流转机制（已按评审建议1补充）

> 原始需求隐含「未开始 → 已开始 → 自然结束」的时序推进，但未明示由定时任务、触发器还是查询时计算实现。本节给出 MVP 推荐方案与连带影响。

**推荐方案：查询时懒计算 + DB 持久化最小化**

- DB `reservation.status` 仅持久化三类**人工/事件驱动**的终态与初态：`PENDING`（未开始，创建后初始态）、`CANCELLED`（人工取消）、`ENDED`（人工提前结束）。
- `ACTIVE`（已开始未结束）与「自然结束」**不落库**，由查询/聚合时按服务端时钟与 `reserve_date + start_time/end_time` 懒计算：
  - `now < reserve_date + start_time` → `PENDING`
  - `reserve_date + start_time ≤ now < reserve_date + end_time` → `ACTIVE`
  - `now ≥ reserve_date + end_time` 且 DB `status == PENDING` → 视为「自然结束」（逻辑等价 `ENDED`，不写回 DB）
  - DB `status` 为 `CANCELLED / ENDED` 时直接以其为准。
- 优点：无需定时任务、无状态写回竞争、无「该流转未流转」的脏数据；适合 MVP 低运维诉求。
- 缺点：查询时需带时钟判定，看板聚合与列表展示需统一封装状态计算函数，避免口径分裂。

**对看板聚合的连带影响**（已按第2轮评审建议1/2与04口径统一）：

- **看板统计口径以 04 分册为准**：看板统计**所有 `status != CANCELLED`** 的预约（含 `PENDING`/`ACTIVE`/`ENDED`），使用**存储态 `status`** 判定，**不走 `computeStatus` 懒计算**；场次=预约数，时长=**原 `end_time - start_time`**。因此本节懒计算**不影响看板统计**——看板不区分 `PENDING`/`ACTIVE`/自然结束，统一按存储态 `status` 与原起止时间计算。
- 懒计算仅作用于**列表展示的状态列**（向用户展示「未开始/进行中/已结束」语义）与**取消/提前结束的可操作性判定**，不参与看板聚合。
- 对「取消时点」的连带影响：取消仅允许作用于「逻辑 `PENDING`/`ACTIVE`」判断结果为 `PENDING` 的记录（即未到开始时间）；进入 `ACTIVE` 后只能「提前结束」不能「取消」。由于 `ACTIVE` 不落库，取消与提前结束的判定函数必须共用同一懒计算逻辑，避免出现「DB 仍为 PENDING 但实际已 ACTIVE 时被错误取消」。
- **提前结束不更新 `end_time`、不引入 `actual_end_time`**，占用时长统一按原 `end_time - start_time` 计算（与 02 BR-RV-48/50、04 DASH-20 统一）。

**隐性需求条目见第 6 节 IMPL-19 / IMPL-20；验收见 AC-NF-26；看板口径见 IMPL-06 / AC-NF-16。**

### 2.4 可靠性补充：并发与缓存设计要点

- **并发抢同一时段**：推荐方案——`reservation` 表上对 `(room_id, reserve_date, start_time, end_time, status)` 建立排他约束（MySQL 无原生排他区间约束，可用应用层 `SELECT ... FOR UPDATE` 锁住该 `room_id + reserve_date` 行集合，再校验区间相交后写入；或使用触发器/应用层分布式锁）。Spec 阶段需给出可落地的 DDL 与代码模式。
- **防重复提交**：前端提交时携带 `Idempotency-Key`，后端 Redis `SETNX` 占位 60s，命中则返回上次结果或拒绝重复提交。
- **看板缓存**：缓存 key 如 `dashboard:by_date:{date}`、`dashboard:by_month:{yyyymm}`，TTL 5 分钟；写操作后主动 `DEL` 对应 key。月维度缓存可由日维度聚合计算后二次缓存。
- **缓存三防**（已按评审建议7补充）：① 空结果短 TTL（60s）缓存防穿透；② TTL 加 ±60s 随机抖动防雪崩；③ 热点 key miss 时互斥锁/single-flight 防击穿（或永不过期 + 异步刷新）。详见 AVAIL-06a。
- **并发对同一预约取消/提前结束**（已按评审建议4补充）：`SELECT ... FOR UPDATE` 锁定目标 `reservation` 行 + 状态机 CAS 校验（`UPDATE ... WHERE id=? AND status=?`，受影响行数=0 即视为已被他人变更，返回 409），保证仅一笔成功流转。

## 3. 安全合规

### 3.1 个人信息最小化

| 编号 | 要求 |
| :-- | :-- |
| COMPL-01 | 用户表仅采集必要字段：`username / password / name / dept_id / role`，不存储身份证、手机号、邮箱等非必要个人信息（如未来扩展通知再加） |
| COMPL-02 | 预约记录仅保留业务必要字段：`room_id / user_id / reserve_date / start_time / end_time / dept_id / title / status`；`title` 由用户填写但限制长度（如 ≤ 50），不收集额外个人备注 |
| COMPL-03 | 看板统计仅按部门、会议室聚合，不输出个人维度的占用排行等可能暴露个人行为的指标（MVP 决策） |
| COMPL-04 | 日志中用户标识仅记录 `username` 或脱敏 `userId`，不记录姓名等可识别信息以外的额外个人数据 |

### 3.2 敏感数据保护

| 编号 | 要求 |
| :-- | :-- |
| COMPL-05 | 密码字段为唯一的敏感数据，必须 BCrypt 哈希；任何接口/日志/导出均不返回明文与哈希值 |
| COMPL-06 | JWT 签名密钥作为后端核心机密，从环境变量读取，不写入源码仓库与交付文档正文 |
| COMPL-07 | 数据库账号 `exam` 仅授予业务库 `exam` 的必要权限（DML + DDL 受控），不使用 root 账号连接应用 |
| COMPL-08 | 备份与导出（如未来支持）需对密码字段脱敏或排除；MVP 不提供数据导出接口 |
| COMPL-09 | 预置账号初始密码在交付文档中明示，但脚本中以哈希值入库；交付文档要求运维部署后立即修改默认密码 |
| COMPL-10 | 考场环境数据为演示数据，不含真实员工个人信息；如需对接真实账号体系应另行评估合规 |

### 3.3 合规边界说明

- 本系统为单位内部行政工具，不涉及对外服务与未成年信息等特殊场景。
- MVP 不实现审计日志落库（仅应用日志），如未来合规要求可追溯操作人/时间，需扩展审计表。
- 不做数据分级与加密存储（密码哈希除外），如未来纳入敏感信息系统等保要求，需补充静态加密与审计。

| IMPL-23 | **并发对同一预约状态变更防护**（已按评审建议4补充） | 预约 + 本分册 | 行锁 + 状态机 CAS，仅一笔成功，余 409 |

## 8. 与其他分册的边界

> **术语区分（已按第2轮评审建议6补充）**：本系统涉及两套「有效集」概念，须避免混淆——
> - **冲突有效集（02 分册，用于冲突判定）**：判定同一会议室同一时段是否可新建预约时所考虑的现存记录集合（排除 `CANCELLED` 等）。
> - **统计有效集（04 分册，用于看板统计）**：看板聚合时所计入的记录集合 = 所有 `status != CANCELLED` 的预约（含 `PENDING`/`ACTIVE`/`ENDED`）。
> 两者口径不同，不可混用；本分册涉及看板口径时一律指「统计有效集」。

- **01 用户与权限**：JWT、密码哈希、越权防护、登录限流等功能性安全规则由 01 分册定义；本分册复核一致并提供横向安全/性能/合规约束。**限流阈值以 01 为准**（SEC-09a 已统一：登录失败 5 次锁定 15 分钟、IP 维度 10 分钟 10 次拒绝 10 分钟）。
- **预约管理分册**：状态机、冲突校验、取消/提前结束的业务时点由其定义；本分册约束其事务、并发、幂等、时区等非功能属性。**提前结束占用时长口径已与 02/04 统一**（已按第2轮评审建议2标注）：提前结束不更新 `end_time`、不引入 `actual_end_time`，占用时长统一按原 `end_time - start_time` 计算（与 02 BR-RV-48/50、04 DASH-20 一致）。
- **会议室管理分册**：会议室字段与增删改规则由其定义；本分册不展开。
- **数据看板分册**：看板维度、指标、空数据态、口径由其定义；本分册约束看板性能、缓存、口径一致性。**看板统计口径已与 04 统一**（已按第2轮评审建议1/4标注）：统计所有 `status != CANCELLED` 的预约（含未开始 `PENDING`），场次=预约数，时长=原 `end_time - start_time`，看板用**存储态 `status`** 判定、不走 `computeStatus`。**衔接要求（04 分册待办）**：04 AC-D-06 应补一条「未开始 PENDING 也计入」的验收，以与本分册 AC-NF-16 对齐。
- **总纲 PRD.md**：由总纲引用本分册；本分册不创建或修改总纲与其他分册文件。
