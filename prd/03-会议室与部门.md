# PRD 分册 03 — 会议室与部门

> 本分册隶属于总纲 `D:\exam\prd\PRD.md`，仅覆盖「会议室主数据」与「部门主数据」两个领域对象：字段维护、状态管理、初始数据预置、停用对预约的影响、容量/位置在表单与列表中的展示，以及显性/隐性需求、业务规则、字段要点、边界条件与验收标准。预约生命周期、用户与权限、数据看板、非功能性需求等由其他分册承载，本文不展开。
>
> 技术栈上下文：Java 17 + Spring Boot 3 / MySQL 8 / Redis 7 / Vue 3 + Element Plus；鉴权采用 JWT。

## 一、概述

本分册负责系统中作为"主数据"存在的两类基础对象：

1. **会议室（Meeting Room）**：预约行为的资源对象。需要维护其基础属性（名称、位置、容量、状态），并支撑预约表单下拉、预约列表展示、看板分组等下游场景。
2. **部门（Department）**：预约人员所属组织维度，也是看板统计维度之一。需预置初始数据，支撑预约表单下拉与看板分组。

两类主数据均由管理员维护、普通员工只读；其状态与字段变更会向下游预约流程传导（如会议室停用影响新建预约、容量字段影响表单展示）。

> 已按评审建议6补充：部门作为组织维度，MVP 不引入停用/启用状态；部门仅通过新增/删除管理生命周期，不承载 `ENABLED/DISABLED` 状态字段。

## 三、隐性需求

### 3.1 会议室停用对预约的影响（重点）

1. **新建预约**：会议室处于 `DISABLED` 状态时，不允许再基于该会议室创建新预约。预约表单下拉中应过滤掉停用会议室；若通过 API 直接提交，后端需返回明确错误码（如"会议室已停用"）。
2. **已有预约**：
   - 已存在且尚未开始的预约（`PENDING`）：建议保持原状，由用户/管理员自行取消；系统不应在停用瞬间自动取消，以免打断既有计划。但可在预约列表中对"会议室已停用"的预约给出提示标记。
   - 已开始的预约（`ACTIVE`）：允许其自然进行或由管理员提前结束，不受停用影响。
   - 已结束/已取消的预约（`ENDED / CANCELLED`）：仅作为历史数据保留，不受影响。
3. **复用语义**：会议室停用后可再次启用（`DISABLED → ENABLED`），启用后恢复可被新预约选择；不存在"永久删除即停用"的隐含等价。
4. **看板维度**：看板中"按会议室"统计时，停用会议室的历史预约仍应统计在内，但可在 UI 上标注"已停用"，避免误以为该会议室当前可用。

### 3.2 会议室容量/位置在预约场景的展示

1. **预约表单**：下拉项需同时呈现容量与位置，便于员工判断会议室是否满足规模与地点需求；建议格式如"第一会议室（A 座 3F，10 人）"。
2. **预约列表**：列表至少展示会议室名称；位置与容量可作为辅助列或悬停提示展示，避免主列过宽。
3. **容量语义**：容量为"可容纳人数上限"，作为参考字段，不在 MVP 阶段强制做"预约人数 vs 容量"的硬校验（人数字段不在本系统核心字段中），仅用于展示与人工判断。

### 3.3 主数据变更对历史预约的影响

- **改名/改位置/改容量**：会议室属性变更后，历史预约在展示时统一取当前主数据值（自然跟随），不保留历史快照。MVP 不引入"历史快照"机制。
- **部门改名**：同上，历史预约的部门展示取当前主数据值。
- **删除**：见 RM-5 / DEPT-5，不物理删除被引用对象，避免历史预约出现 `null` 会议室/部门。

### 3.4 并发与一致性

- 会议室状态切换（启用↔停用）需保证与并发的新建预约请求之间的时序：若状态切换与预约提交并发，停用一旦生效，后续新建预约必须失败；已在事务中校验通过的预约不回滚。
- 删除/编辑主数据时需对并发更新做乐观锁或行锁保护，避免脏写。

### 3.5 空数据态

- 系统首次部署后，会议室与部门表均应有初始数据，避免员工进入预约表单时下拉为空。
- 即使管理员后续清空所有启用会议室，预约表单应显示"暂无可选会议室"的友好提示，而非空白下拉。

## 四、业务规则

### 4.1 会议室业务规则

| 编号 | 规则 |
| :-- | :-- |
| BR-R1 | 会议室名称在系统内唯一（仅限未软删除记录范围内，即 `deleted_at IS NULL`），不允许重名（含启用与停用状态之间）；是否包含已软删除记录的判定见第六节边界条件第 11 条——已按评审建议4/8补充 |
| BR-R2 | 容量为正整数，取值范围 1 ≤ capacity ≤ 1000 |
| BR-R3 | 位置为非空字符串，最大长度 100 字符 |
| BR-R4 | 名称非空，最大长度 50 字符 |
| BR-R5 | 状态仅允许 `ENABLED` / `DISABLED` 两种取值；新建默认 `ENABLED` |
| BR-R6 | 只有 `ADMIN` 角色可执行增删改；`EMPLOYEE` 仅可查询 |
| BR-R7 | 被任意预约记录引用（含 `ENDED/CANCELLED` 历史预约，即"历史预约引用亦阻止物理删除"）的会议室不允许物理删除，统一采用软删除（写入 `deleted_at`）；未被任何预约引用的会议室可软删除——已按评审建议1/2补充 |
| BR-R8 | 停用会议室不参与新预约创建；已存在预约保留，不做自动取消 |
| BR-R9 | 列表查询支持按名称模糊匹配、按状态精确过滤；支持分页；列表默认排除 `deleted_at IS NOT NULL` 的软删除记录 |
| BR-R10 | 会议室创建时间由系统自动写入，不可手动修改；`updated_at` 由系统在更新时自动写入 |
| BR-R11 | 会议室更新采用乐观锁字段 `version`（初值 0），更新时 `version+1` 并校验版本一致——已按评审建议10补充 |

### 4.2 部门业务规则

| 编号 | 规则 |
| :-- | :-- |

| BR-D2 | 名称非空，最大长度 50 字符 |
| BR-D3 | 只有 `ADMIN` 角色可执行增删改；`EMPLOYEE` 仅可查询 |
| BR-D4 | 被用户或任意预约记录引用（含 `ENDED/CANCELLED` 历史预约，即"历史预约引用亦阻止物理删除"）的部门不允许物理删除，统一采用软删除（写入 `deleted_at`）；未被任何引用的部门可软删除——已按评审建议1/2补充 |
| BR-D5 | 部门编辑不应影响历史预约的展示（自然跟随当前值） |

| BR-D8 | 部门更新采用乐观锁字段 `version`（初值 0），更新时 `version+1` 并校验版本一致——已按评审建议10补充 |

## 五、数据/字段要点

### 5.1 会议室表 `meeting_room`

| 字段 | 类型 | 约束 | 说明 |
| :-- | :-- | :-- | :-- |
| id | BIGINT | 主键，自增 | 会议室 ID |
| name | VARCHAR(50) | NOT NULL | 会议室名称 |
| location | VARCHAR(100) | NOT NULL | 位置描述 |
| capacity | INT | NOT NULL，CHECK ≥ 1 | 容量（人数上限） |
| status | VARCHAR(10) | NOT NULL，默认 `ENABLED` | 启用/停用枚举 |
| version | INT | NOT NULL，默认 0 | 乐观锁版本号，更新时 +1——已按评审建议10补充 |
| created_at | DATETIME | NOT NULL，默认当前时间 | 创建时间 |
| updated_at | DATETIME | NOT NULL，默认当前时间，更新时自动刷新 | 最近更新时间 |
| deleted_at | DATETIME | NULL，默认 NULL | 软删除标记，非 NULL 表示已软删除——已按评审建议1补充 |

- 索引建议：`status` 单列索引（列表过滤高频）；`name` 唯一索引须配合软删除改造为复合唯一索引 `uk_room_name_active (name, (CASE WHEN deleted_at IS NULL THEN 0 ELSE id END))` 或采用 `name + deleted_at` 复合唯一索引，使软删除后名称释放、可被新建复用（最终形态以 Spec 阶段定稿，详见第六节边界条件第 11 条）。
- 枚举在应用层以常量/枚举类维护，DB 层以字符串存储。

| 字段 | 类型 | 约束 | 说明 |
| :-- | :-- | :-- | :-- |

| name | VARCHAR(50) | NOT NULL | 部门名称 |
| version | INT | NOT NULL，默认 0 | 乐观锁版本号，更新时 +1——已按评审建议10补充 |
| created_at | DATETIME | NOT NULL，默认当前时间 | 创建时间 |
| updated_at | DATETIME | NULL，更新时自动刷新 | 最近更新时间——已按评审建议3补充 |
| deleted_at | DATETIME | NULL，默认 NULL | 软删除标记，非 NULL 表示已软删除——已按评审建议1补充 |

## 六、边界条件

1. **空字符串与纯空格**：名称、位置不可为空字符串或仅空格；前后端均需 `trim` 后非空校验。
2. **容量边界**：capacity = 1 合法；capacity = 0 或负数非法；capacity 超过 1000 视为非法（防止误填如 99999）。
3. **状态非法值**：传入非 `ENABLED`/`DISABLED` 的状态值应被拒绝。
4. **重名大小写/空格**：`"第一会议室"` 与 `" 第一会议室 "` 应视为重名；建议存储前 `trim`，唯一索引区分大小写按 DB 默认 collation，需在 Spec 阶段确认。
5. **删除被引用对象**：尝试删除被引用的会议室/部门时，返回业务错误而非 500，错误信息明确提示"已被预约/用户引用，无法删除"。
6. **停用与新建预约并发**：见 3.4，需保证停用生效后新建预约不可成功。
7. **跨页排序**：会议室列表默认按 `id` 升序；部门列表默认按 `id` 升序。
8. **创建时间**：由后端写入，前端不传；若前端传入应被忽略。
9. **空数据态**：初始数据未加载或被清空时，下拉与列表需有友好空状态文案。
10. **超大字段**：名称 50、位置 100 字符上限需在 DTO 层校验，超出返回参数校验错误。
11. **软删除与唯一性**（已按评审建议4补充）：采用软删除方案后，`name` 唯一性范围限定为"未软删除记录"（`deleted_at IS NULL`）。实现方式二选一，最终在 Spec 阶段定稿：(a) 复合唯一索引 `(name, deleted_at)`，软删除时 `deleted_at` 置为当前时间戳从而释放名称，允许新建同名记录；(b) 软删除时对 `name` 追加后缀（如 `__deleted_<id>_<ts>`）释放原名称。无论哪种方式，BR-R1/BR-D1 中"系统内唯一"均指"未软删除范围内唯一"，已软删除记录不参与重名校验。

## 七、验收标准

### 7.1 会议室

| 编号 | 验收点 | 预期 |
| :-- | :-- | :-- |
| AC-R1 | 管理员新增会议室 | 合法字段提交后入库，返回新增 id；列表可见 |
| AC-R2 | 普通员工尝试新增 | 返回 403/权限错误，数据不入库 |
| AC-R3 | 会议室重名 | 返回业务错误"名称已存在" |
| AC-R4 | 容量 0 或负数 | 返回参数校验错误 |
| AC-R5 | 停用会议室后新建预约 | 该会议室不在表单下拉中；API 直接提交返回"会议室已停用" |
| AC-R6 | 停用会议室后查看已有预约 | 历史 `PENDING` 预约仍存在，未被自动取消；列表对停用项有提示 |
| AC-R7 | 重新启用会议室 | 状态切回 `ENABLED` 后，可再次被新预约选择 |
| AC-R8 | 删除被引用会议室（含仅被历史/已取消预约引用） | 已按评审建议2补充：无论被有效预约还是仅被 `ENDED/CANCELLED` 历史预约引用，均返回业务错误"已被预约引用，无法删除"，不物理删除 |
| AC-R9 | 删除未被引用会议室 | 已按评审建议5补充：返回成功，记录软删除（`deleted_at` 置为当前时间），列表、详情、下拉均不再返回该记录；数据库中记录仍存在，`deleted_at` 非空 |
| AC-R10 | 列表按名称模糊查询 | 输入"会议"可命中含"会议"的记录 |
| AC-R11 | 列表按状态过滤 | 选 `ENABLED` 仅返回启用项 |
| AC-R12 | 预约表单下拉 | 下拉项格式含名称+位置+容量，且仅含启用项 |
| AC-R13 | 预约列表展示 | 列表行可见会议室名称，位置/容量可查看 |

| AC-D4 | 普通员工尝试编辑/删除 | 返回 403/权限错误 |
| AC-D5 | 删除被引用部门（含仅被历史/已取消预约引用） | 已按评审建议2补充：无论被有效预约还是仅被 `ENDED/CANCELLED` 历史预约引用，均返回业务错误"已被引用，无法删除"，不物理删除；软删除后列表与下拉不再返回 |
| AC-D6 | 预约表单部门下拉 | 下拉展示全部部门，本人默认选中所属部门 |
| AC-D7 | 部门改名后历史预约展示 | 历史预约显示为新名称（自然跟随） |

## 八、与其他分册的衔接关系

- **预约分册**：本分册定义会议室/部门主数据，预约表单下拉、预约列表展示、看板分组均依赖此处的字段与状态规则；会议室停用对新建预约的拦截规则由预约分册在冲突校验环节引用。
- **用户权限分册**：本分册的"管理员可增删改、员工只读"由权限分册统一鉴权落地；本分册只声明权限要求。
- **看板分册**：看板按会议室/部门维度统计时，名称取主数据当前值；停用会议室的历史预约纳入统计并在 UI 标注。
- **数据/Spec 分册**：字段类型、索引、枚举值、初始数据 SQL 以 Spec 阶段为准，本分册提供需求侧依据。
- **审计日志**（已按评审建议11补充）：主数据增删改的操作审计日志不在 MVP 范围，后续可在 Spec 阶段评估是否引入操作日志表（记录操作者、时间、操作类型、变更前后快照）。
