## 1. 项目背景与业务目标

### 1.1 业务背景
在单位行政日常办公管理中，会议室作为高频共享核心资源，长期面临以下突出痛点：
- **时段冲突频发**：依赖线下纸质登记、口头报备或即时聊天工具沟通，极易发生多人抢占同一会议室同一时间段的情况，导致会议延误、组织混乱；
- **权限与秩序失控**：缺乏规范的准入与操作机制，存在代订、私自抢占、随意取消他人会议等管理失序行为；
- **资源浪费与僵尸占用**：会议提前结束后未及时释放资源，或预约后无人参会形成“僵尸会议室”，其他人无法再次预约利用；
- **利用率缺乏量化洞察**：行政管理人员无法精准掌握各会议室的实际排期负荷与各部门的资源占用频次，缺乏客观的数据支撑以进行场地调配与资产优化。

### 1.2 建设目标
为彻底解决上述行政管理难题，本项目建设一套面向单位内部的轻量化、高可用、体验友好的**全 Web 端「会议室预约系统」**，达成以下业务与技术目标：
1. **零冲突排期保障**：构建数学化严谨的时段冲突判定算法，配合数据库行级锁排他控制，从系统底层彻底杜绝“双重预约”与时段重叠。
2. **权责明晰的生命周期闭环**：确立“普通员工”与“系统管理员”两级角色治理体系，提供涵盖“创建预约 → 时钟推进自然流转 → 取消释放 → 提前结束”的全生命周期受控管理。
3. **多维直观的数据看板**：提供按“日期 / 月份”双维度的会议室与部门场次、占用时长对比看板，通过 ECharts 图表直观呈现单位会议资源负荷全貌。
4. **轻量极简的人机交互**：严格限定全 Web 端交互，聚焦“预约列表”、“预约表单”、“数据看板”三大核心功能页面，实现低上手成本、无歧义的极速操作体验。

### 3.3 核心环境与时区约定
1. **统一时区口径**：容器系统时区、JVM 启动参数（`-Duser.timezone=Asia/Shanghai`）、MySQL 数据库连接串（`serverTimezone=Asia/Shanghai`）统一锁定为东八区（`Asia/Shanghai`, UTC+8）。前后端交互日期格式固定为 `YYYY-MM-DD`，时间格式固定为 `HH:mm:ss`（或 `HH:mm`），不携带外部时区偏移。

### 4.2 实体关键约束与关联语义
1. **User（用户）**：
   - `username` 全局唯一且统一强制转换为小写存储与校验。
   - `role` 为单值枚举（`EMPLOYEE / ADMIN`），MVP 不支持一人多角色。
   - `dept_id` 允许为空（如超级管理员可不挂载具体业务部门）。
2. **Department（部门）**：
   - 组织架构主数据，`name` 在未删除范围内唯一。
   - 部门不可被物理删除，凡已被用户或预约表引用的部门，仅允许软删除（写入 `deleted_at`）。
3. **MeetingRoom（会议室）**：
   - 预约的物理载体，`name` 在未删除范围内唯一；`status` 枚举限定为 `ENABLED`（启用）或 `DISABLED`（停用）。
   - 被历史或当前预约引用的会议室禁止物理删除，仅允许软删除（写入 `deleted_at`）。
4. **Reservation（预约）**：
   - 业务核心交易表。通过 `(room_id, reserve_date)` 划分排他校验空间；
   - 强制记录冗余快照字段 `room_name`、`dept_name`、`user_name`，实现历史可追溯性解耦。

## 5. 全局统一核心决策（贯穿各分册）

为确保 5 份分册以及后续原型、规格、编码、测试之间逻辑严丝合缝、完全闭环，确立以下 6 大顶层核心裁定：

### 决策 1：时段冲突判定规则（半开区间互斥）
- **区间定义**：预约占用时段统一采用**左闭右开区间 `[start_time, end_time)`**。
- **数学相交判定**：对同一 `room_id` 且同一 `reserve_date`，待定新区间 `[s_new, e_new)` 与已有有效记录 `[r.start_time, r.end_time)` 发生冲突，当且仅当满足：
  $$\text{Overlap} \iff (r.\text{start\_time} < e\_new) \land (s\_new < r.\text{end\_time})$$
  *(等价于非冲突判定：$e\_new \le r.\text{start\_time} \lor r.\text{end\_time} \le s\_new$)*
- **边界裁定**：
  - 相邻时段允许无缝拼接（如上一场 `09:00~10:00`，下一场 `10:00~11:00`，`10:00` 属于开区间终点与闭区间起点的交接，**判定为不冲突**）。
  - 起止相等（`start_time == end_time`）判定为非法参数（时长为 0 拒绝）。
  - **强制拒绝过去时段**：服务端在创建时比对当前时钟，若 $\text{combine}(reserve\_date, start\_time) < now$，立即拒绝提交，**MVP 严禁补录过去时段**。

### 决策 2：状态二元口径机制（存储态 vs 即时态，决策 E）
系统确立**“存储态驱动看板，即时态驱动流转与展示”**的二元解耦口径：
- **数据库存储态（`status`）**：
  - 存储值仅持久化：`PENDING`（初始创建态）、`CANCELLED`（人工取消）、`ENDED`（人工提前结束或定时落库终态）。
  - 在 MVP 推荐的方案 A（懒计算）下，`ACTIVE` 状态**不落库**（数据库 CHECK 约束保留 ACTIVE 仅作枚举完整性防御）。
  - **看板聚合统计统一按存储态过滤**：看板直接统计数据库中 `status != 'CANCELLED'` 的全部记录，不执行时间轴推算，保障聚合查询的高性能与结果稳定性。
- **业务即时态（`computeStatus(record, now)`）**：
  - 用于前端**预约列表、详情状态展示**以及**取消/提前结束操作的前置合法性校验**。
  - 计算逻辑：
    - 若持久化 `status == CANCELLED` $\to$ 返回 `CANCELLED`；
    - 若持久化 `status == ENDED` $\to$ 返回 `ENDED`；
    - 若 $now < \text{combine}(reserve\_date, start\_time)$ $\to$ 返回 `PENDING`；
    - 若 $\text{combine}(start\_time) \le now < \text{combine}(end\_time)$ $\to$ 返回 `ACTIVE`；
    - 若 $now \ge \text{combine}(reserve\_date, end\_time)$ $\to$ 返回 `ENDED`（自然结束）。
  - **防误操作连带保障**：存储态虽为 PENDING，但若时钟已进入开会时段，`computeStatus` 实时计算为 ACTIVE，此时调用取消接口会被拦截并提示“会议已开始不可取消”，只能执行提前结束。

### 决策 3：提前结束与占用时长口径（决策 A）
- **字段与状态处理**：
  - 执行提前结束时，系统仅将记录的 `status` 置为 `ENDED`，更新 `updated_at`。
  - **严禁修改 `end_time` 原始值，严禁在数据库中引入 `actual_end_time` 等冗余字段**。
- **剩余时段排他语义**：
  - 提前结束后的原预约时段在其原 `[start_time, end_time)` 全区间内**仍保持占位，不予释放**给他人预约，杜绝因碎裂时段再预约引发的排期争议。
- **时长统计口径**：
  - 系统内所有“占用时长”计算公式全局高度统一：$$\text{Duration} = end\_time - start\_time$$
  - 无论预约是自然结束还是提前结束，均严格按原始起止时间差（分钟）计算，杜绝统计口径混乱。

### 决策 4：数据看板统计口径（决策 B）
- **统计对象范围**：选定日期或月份范围内，所有数据库存储态满足 `status != 'CANCELLED'` 的有效预约（完整覆盖 `PENDING`、`ACTIVE`、`ENDED`）。
- **指标聚合口径**：
  - **场次**：符合条件的有效预约记录行数（`COUNT(*)`）。
  - **占用时长**：符合条件的有效预约原始时间差总和（`SUM(TIMESTAMPDIFF(MINUTE, start_time, end_time))`）。
- **全主数据覆盖展示**：看板图表 X 轴以当前会议室和部门的**全量主数据**为基准呈现；对于在统计区间内场次为 0、时长为 0 的会议室或部门，必须在图表中完整绘制（柱高为 0），直观反映资源闲置态。

### 5. 预约表冗余快照机制
- **快照字段持久化**：在创建预约落库时，强行冗余写入当时的 `room_name`、`dept_name`、`user_name`。
- **改名与软删除解耦**：当会议室、部门被管理员改名，或相关会议室、部门、用户被软删除时，历史预约记录在列表与详情中的名称展示**直接读取快照值**，并在界面上打上“（已停用）/（已删除）”退化标签，彻底解决关联实体悬空或历史信息失真风险。

### 6. 账号与数据完全隔离原则
- **虚构预置数据准则**：系统初始化脚本（`V1.0__init_data.sql`）中的所有部门（研发部、产品部、市场部、行政部、财务部）、会议室（第一会议室、第二会议室、大会议室等）及测试账号一律采用**完全虚构的示例数据**。
- **凭据硬性红线**：**严禁在代码、SQL 脚本、PRD 文档及交付产物中引用或泄露 `desc.md` 考试机表格中的任何真实个人姓名（如张俊杰）、云电脑账号密码、主机名、公网 IP（202.101.223.46）或中间件端口密码**。

## 8. 全局非功能性指标与合规总览

### 8.1 性能指标基准 (Performance SLA)

> **测试基准说明**：以考场单机或局域网服务器（8 Core / 16G RAM）为压测基准环境，使用 JMeter 预热 30s 后采样 3 分钟，剔除冷启动干扰。

| 序号 | 核心场景 | 并发规模 / 压力条件 | P95 响应时延目标 | 核心保障机制与实现方案 |
| :-- | :-- | :-- | :-- | :-- |
| **P-01** | **并发抢占同一时段** | 100 并发线程瞬间抢占同一会议室同一时段 | **P95 ≤ 800 ms** | DB 行锁 `SELECT ... FOR UPDATE` + 事务内冲突判定，保证仅 1 笔成功，99 笔返回 409 |
| **P-02** | **并发取消/提前结束** | 50 并发请求对同一预约执行状态流转 | **P95 ≤ 600 ms** | DB 行级互斥锁 + 状态机 CAS 原子更新（受影响行数 = 0 则拦截并提示） |
| **P-03** | **数据看板日维度查询** | 单日数据聚合（1000 笔预约规模，命中缓存） | **P95 ≤ 200 ms** | 命中 Redis 缓存；若穿透回源 DB，冷查 P95 ≤ 1.5 s |
| **P-04** | **数据看板月维度查询** | 整月数据聚合（3000 笔预约规模） | **P95 ≤ 2.5 s** | 缓存 TTL 15 分钟，写操作主动失效受影响月份 key，防全表扫描 |
| **P-05** | **预约列表筛选与分页** | 高频组合筛选（会议室+日期+状态），20条/页 | **P95 ≤ 800 ms** | 依托 `(room_id, reserve_date, start_time)` 覆盖索引，严禁全表扫 |
| **P-06** | **用户认证登录** | 携带密码的登录请求 | **P95 ≤ 500 ms** | BCrypt 计算（cost=10），合理分配线程算力 |
| **P-07** | **前端首屏加载速度** | 生产环境 Nginx Gzip 托管 | **≤ 3.0 s** | Vite 现代打包代码分割、组件按需引入、无外网 CDN 阻塞 |

### 8.2 安全合规与防护总览

1. **凭据加固与密码学合规**：
   - 数据库中 `user.password` 一律存储 BCrypt（Cost ≥ 10）加盐哈希串，源码及可执行构建物内严禁出现任何明文密码；
   - 密码强度约束：长度 8~64 位，必须包含字母与数字，前后端双向阻断弱口令。
2. **凭证防窃取与会话安全**：
   - 前端采用 **Pinia 内存持有 Token**、**sessionStorage 作为刷新会话恢复兜底**；
   - **严禁使用 `localStorage`**（防御持久型 XSS 窃取），**严禁写入 Cookie**（天然免疫 CSRF 攻击）；
   - JWT 签名采用安全密钥（≥ 256-bit 随机熵，环境变量注入），载体注入唯一 UUID `jti`，登出时将 `jti` 写入 Redis 维护黑名单。
3. **注入与脚本攻击纵深防御**：
   - **SQL 注入**：MyBatis 参数必须全部使用 `#{}` 预编译占位符，严禁使用 `${}` 拼接动态表单；排序列名必须走白名单枚举映射；
   - **XSS 跨站脚本**：Vue 3 模板默认转义文本，严禁对预约标题 `title` 使用 `v-html` 渲染；服务端输出统一进行必要字符过滤。
4. **接口反爬与防暴破限流体系**：
   - **账号维度锁**：单个用户名 15 分钟内连续 5 次密码错误，**当次触发锁定 15 分钟**，锁定期内即使用户输入正确密码亦直接拒绝；
   - **IP 维度熔断**：单个客户端 IP 10 分钟内累计发生 10 次登录失败，全 IP 临时拒绝请求 10 分钟；
   - **接口级防抖**：同一用户预约创建接口限频 1 次 / 3 秒，配合 Redis 幂等 Key 拦截重复请求。
5. **合规最小化与数据隐私**：
   - 用户表不采集身份证、手机号、家庭住址等无关个人数据；
   - 日志输出前严格执行脱敏，严禁输出明文密码、完整 JWT 串、真实手机号等涉密字段。

---

### 8.3 可靠性与故障降级设计

1. **分布式并发防重双保险**：
   - 前端防抖禁用按钮 $\to$ Redis 幂等排他占位（`SETNX EX 5s`） $\to$ 数据库事务内行锁校验，三道防线层层收敛。
2. **Redis 异常容错与优雅降级**：
   - 若 Redis 发生单点宕机或网络中断，系统自动执行降级策略：
     - 鉴权逻辑：降级为仅依据 JWT 签名与有效期校验放行，日志打印 WARN 告警；
     - 防重逻辑：记录日志并放行请求，完全依托 MySQL 事务排他锁保障排期唯一性；
     - 看板查询：自动降级回源直连 MySQL 聚合查询，保证行政人员业务不中断。
3. **容器探针隔离机制**：
   - `/api/health/liveness`：仅探活进程与 JVM 存活性，作为 Docker 容器存活检测；
   - `/api/health/readiness`：检测 DB、Redis 连接就绪度，且响应体**严禁透出任何主机 IP、端口、连接串**等拓扑机密。
